Propósito y alcance

Diseñar y presentar un prototipo web de comercio electrónico para la venta de calcetines inspirados en películas, series y cultura pop, acompañado de un modelo de arquitectura de software bajo el paradigma 4+1. La solución considera catálogo, carrito, checkout, inventario y reseñas; la documentación distingue los flujos simulados de las capacidades que necesitan servicios de backend.

Alcance de esta entrega

El catálogo lee productos.json y los datos de carrito, pedidos, reseñas y administración se guardan en localStorage. No existe servidor, autenticación real ni sincronización de inventario entre visitantes.

DOCUMENTO 02 / ANÁLISIS

Necesidades del negocio.

El caso de estudio presenta a Sockbuster como un comercio electrónico emergente que necesita reforzar su presencia digital y planificar una estructura escalable. A partir de esta necesidad se identifican los siguientes objetivos:

01

Descubrimiento

Organizar productos por colecciones temáticas y mostrar precio, disponibilidad y tallas para facilitar la elección.

02

Compra

Reunir productos en un carrito, modificar cantidades y ofrecer confirmación identificable de la compra simulada.

03

Operación

Definir la administración de modelos, asociaciones culturales, stock y precios con acceso restringido.

04

Comunidad

Diseñar una experiencia de reseñas y puntuaciones atribuibles a clientes registrados.

Límites y supuestos

  • Los artículos, precios y niveles de stock se leen desde data/productos.json y son ficticios; las modificaciones locales no alteran el JSON publicado.
  • La verificación de pago es simulada y no integra una pasarela financiera.
  • Los roles Cliente y Administrador, el servidor REST y la base de datos representan la arquitectura objetivo, no servicios actualmente desplegados.
DOCUMENTO 03 / RF01—RF04

Requisitos funcionales.

RF01

Catálogo por colecciones temáticas

DEMO OPERATIVA

Actores: visitante y cliente registrado. El usuario explora y filtra calcetines de Ciencia Ficción, Terror 80s, Drama y Animación. Cada ficha muestra una representación visual del artículo, precio, stock, tallas y valoración.

Flujo: abrir catálogo → seleccionar categoría, talla, precio o búsqueda → actualizar resultados → examinar producto.

Aceptación: los filtros combinados modifican los resultados sin recargar la página y la tarjeta presenta los datos solicitados. Las imágenes actuales son representaciones ilustrativas, no fotografías del producto.

TRAZA: Vista Lógica · Escenarios · catalogo.html
RF02

Carrito y gestión de pedidos

SIMULACIÓN OPERATIVA

Actores: visitante y cliente registrado. El cliente agrega calcetines, cambia cantidades, elimina ítems y simula el checkout ingresando nombre, correo y dirección.

Flujo: agregar artículo → ajustar carrito → iniciar checkout → validar datos y stock de prueba → confirmar → mostrar total y código único SB.

Aceptación: el pedido contiene ítems, cantidades, precios, fecha y total; el código es generado automáticamente y el carrito se vacía tras confirmar. No se realizan cobros ni pedidos reales.

TRAZA: Vista de Procesos · Escenarios · catalogo.html
RF03

Administración de inventario y temáticas

DEMO LOCAL DISPONIBLE

Actor: administrador autenticado. Se requiere registrar modelos, asociarlos con una película o serie, editar existencias y actualizar precios.

Flujo objetivo: iniciar sesión → autorizar rol administrador → crear o editar producto → validar campos y persistir cambios → reflejar el inventario actualizado en catálogo.

Aceptación parcial: el panel permite editar y exportar JSON, pero no autentica administradores ni persiste cambios en servidor. El panel admin.html permite editar productos, stock y precios exclusivamente en localStorage. No hay control de acceso ni sincronización compartida.

TRAZA: Vista Lógica · Vista de Desarrollo · Escenarios
RF04

Reseñas de fanáticos

DEMO LOCAL PARCIAL

Actor: cliente registrado. Debe valorar cada modelo con 1–5 estrellas y publicar comentarios en la ficha de producto.

Flujo objetivo: autenticar cliente → abrir reseñas del producto → calificar y comentar → validar y guardar → recalcular puntuación media.

Aceptación parcial: el formulario, la puntuación y el comentario funcionan en el navegador, pero faltan autenticación de clientes y almacenamiento remoto para cumplir exactamente lo exigido.

TRAZA: Vista Lógica · Escenarios · catalogo.html
DOCUMENTO 04 / RNF01—RNF02

Requisitos no funcionales.

RNF01

Despliegue y rendimiento

PARCIALMENTE VERIFICADO

Exigencia: interfaz alojada en un servicio cloud y carga inicial inferior a 2 segundos.

Evidencia: archivos estáticos preparados para publicarse en GitHub Pages. La publicación pública y las pruebas de rendimiento quedan pendientes, por lo que no se afirma el cumplimiento de <2 segundos.

TRAZA: Vista Física · sitio global
RNF02

Seguridad y autenticación

JWT PENDIENTE

Exigencia: HTTPS entre navegador y servicios, y tokens JWT para operaciones administrativas.

Evidencia: GitHub Pages ofrece HTTPS al publicar el repositorio. Esta versión no contiene API, tokens JWT ni autenticación administrativa segura; el panel es un simulador local.

TRAZA: Vista Física · Vista de Desarrollo

DOCUMENTO 06 / MODELO CONCEPTUAL

Modelo de información.

La vista lógica define las entidades del dominio. El siguiente resumen presenta sus responsabilidades y relaciones principales; los nombres y atributos detallados aparecen en el diagrama de clases.

ENTIDADDATOS RELEVANTESRELACIÓN

ProductoCalcetintítulo, temática, precio, stock, tallas, imagenPertenece a colección; recibe reseñas
ColeccionTematicaid, nombre, tema cultural, descripciónContiene productos
Carrito / ItemCarritocantidad, precio unitario, totalContiene ítems que referencian productos
Pedido / DetallePedidocódigo único, fecha, estado, totalRegistra detalles y cantidades
Reseñaestrellas, comentario, fechaLa escribe un cliente para un producto

Reglas de negocio

  1. La cantidad solicitada debe ser mayor que cero y no superar la disponibilidad declarada.
  2. El importe del pedido es la suma de cantidad por precio unitario de cada detalle.
  3. Cada pedido confirmado recibe un identificador único del formato SB-....
  4. Las puntuaciones válidas son enteros del 1 al 5.
  5. En el sistema objetivo, solo administradores autorizados pueden modificar precios y stock; solo clientes registrados pueden publicar reseñas.

DOCUMENTO 09 / ENTREGA

Entrega y próximos pasos.

Entregables exigidos por la guía

  • Sitio con las tres páginas obligatorias: inicio, catálogo y arquitectura UML. Esta página de documentación es un anexo adicional.
  • Cinco vistas de arquitectura 4+1 con diagramas UML y explicación.
  • Repositorio de código público que contenga web y documentación, con un archivo README y el enlace al despliegue.
  • Sitio disponible públicamente en línea para la evaluación.
  • Nombre completo de cada estudiante en la página de inicio.
Elementos de entrega aún no acreditados

La carpeta está preparada para GitHub Pages, pero todavía no reemplaza un repositorio público publicado. Falta el enlace público al repositorio y la publicación con acceso abierto. Además, RF03, la autenticación de RF04 y JWT requieren backend real para afirmar cumplimiento total.

Tecnología y despliegue actual

La versión usa exclusivamente HTML5, CSS3, JavaScript ES6+, productos.json y localStorage. Los diagramas originales plantean una arquitectura futura con backend, base de datos y JWT; las fuentes PlantUML actualizadas en la entrega muestran el despliegue estático real.
